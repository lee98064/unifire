# WP11 — Incident correlation timeline + monthly infrastructure report

Read `docs/codex/BRIEF.md`, `docs/PLAN-infra.md`, `shared/schemas/infra.ts` (Incident*, InfraReport), and the
WP8–WP10 code (device sampler events, port-health events, topology builder, audit service, snapshots).
Endpoints marked `WP11` in `shared/api.ts` are in scope, plus rule trigger `incident.opened`, notifications
`incident_opened` / `incident_resolved`, `DashboardSummary.infra.openIncidents` / `.incidents`.

The point of this feature: when something breaks, the user gets **one** notification and **one** card that
says what probably broke first ("Core Switch rebooted → 2 APs offline → 19 clients dropped; 3 min earlier
someone changed the port profile in UniFi"), instead of a flood of single alerts.

## 1. Signals (`server/engine/infra/incidents/signals.ts`)
Subscribe to engine events and turn them into `IncidentSignal`s (persist in `incident_signals`, with
`incidentId` nullable until attached):
| kind | from | failure? |
|---|---|---|
| egress_down / egress_up | `egress.down` / `egress.up` | down = failure |
| wan_down / wan_up | gateway WAN status change (`server/unifi/wan.ts`) | down = failure |
| device_offline / device_online | `infra.offline` (immediate, not the rule delay) / `infra.online` | offline = failure |
| device_rebooted | `infra.rebooted` with `unexpected: true` (Unifire restarts are ignored) | failure, auto-recovers when the device is online again |
| uplink_down / uplink_up | link down/up on a port whose peer is an adopted device (port-health) | down = failure |
| port_issue | `port.issue` | joins incidents only — never opens one alone, except `flapping` |
| mass_disconnect / clients_returned | ≥ `massDisconnectMin` **and** ≥ `massDisconnectPct` % of a device's clients disconnect within 2 min (group `client.disconnected` by uplink AP/switch); returned when ≥ 70 % are back | disconnect = failure |
| config_change | audit events with actor `external` or `unifire` in categories config/route/wifi/poe/device | never a failure; becomes a **suspect** |
Severity per signal: error for offline/down/mass, warning otherwise. i18n `incident.signal.<kind>` with params
`{name, port, count, ago}`.

## 2. Correlation (`server/engine/infra/incidents/correlate.ts` — pure, heavily tested)
- A failure signal **joins** an open incident if it arrives within `settings.incidents.windowMinutes` of that
  incident's latest signal **and** is related: its device is an ancestor/descendant of any device already in
  the incident (topology parent chain from the WP10 builder at signal time), or both are "global"
  (WAN/egress/gateway), or it is a mass_disconnect/port_issue on a device in the incident's subtree. Otherwise a
  failure signal **opens** a new incident (port_issue except flapping never opens).
- **Root**: among failure signals, the most upstream device (smallest depth), tie → earliest; global signals
  (WAN/egress) win over devices when they are earliest. Title `incident.title.<root kind>` with params
  `{name, devices, clients, people}` (counts as strings).
- **Suspects**: config_change signals in [openedAt − 15 min, openedAt] → attached with `suspect: true`.
  `IncidentDetail.diff` = latest snapshot before the earliest suspect and the first snapshot after it (or
  `toSnapshotId: null` = live).
- **Impact**: devices = failed devices plus their downstream devices; clients = sum of their last-known client
  counts; people = people whose presence devices hung off those devices; egresses = egresses down.
- **Severity**: critical when the gateway is offline, all WANs are down, all egresses are down, or affected
  clients ≥ 50 % of online clients before the incident; else warning. Can escalate, never de-escalates.
- **Resolve**: every failure signal has its recovery (online/up/returned; rebooted counts as recovered once
  the device is online) and `quietMinutes` passed with no new failure → `resolved`, `resolvedAt` = last
  recovery. Recovery signals are attached to the incident.
- `affectedNodes` = topology node ids (`dev:<mac>`, their client groups, `egress:<id>`).

## 3. Outputs
- Notifications: `incident_opened` once when opened (if severity ≥ `settings.incidents.notifyMinSeverity`;
  `off` = never), and once more if it escalates to critical; `incident_resolved` with duration. Per-signal
  notifications that already exist (egress_down …) stay as they are. Push action: "open" → `/insight/incidents/<id>`.
- Rule trigger `incident.opened {minSeverity}` (event payload: id, title params, severity).
- Live `incident {id, status, severity}`; dashboard fields; audit entries (category `system`).
- API: `GET /api/incidents` (cursor paging, status filter, open first then newest), `GET /api/incidents/:id`,
  `PATCH /api/incidents/:id` (acknowledged, note). Retention 1 year.

## 4. Monthly infrastructure report — `GET /api/reports/infra?month=YYYY-MM` (`InfraReport`)
Per device: availability (online fraction of sampled minutes), downtime, number of outages, unexpected reboots,
firmware changes, avg CPU/mem, max temp, port events. Incidents: count, critical, total duration, MTTR,
counts by root kind, 5 longest. `energyWh` from the WP9 ledger. Month boundaries in the settings timezone.
`coverage` = sampled minutes / minutes in the month so far.

## 5. Mock

`reboot-ap` → warning incident that auto-resolves; a mock external config change shortly before
`offline-switch` (new scenario `config-then-outage`) shows up as a suspect.

## Tests
Correlation: switch reboot → child AP offline → mass disconnect = one incident, root = switch; two unrelated
device outages = two incidents; WAN down + egress down = one global incident; port downgrade alone does not
open; flapping does; suspect window; severity escalation; resolution after quiet period, new failure during
quiet keeps it open; Unifire-initiated restart ignored. Report: availability with sample gaps, MTTR, month
boundaries in Asia/Taipei.

## 6. Follow-ups from the WP9/WP10 reviews (do these too)
- **Planned PoE-off is not an outage.** A device that is offline because Unifire holds its powering port off
  (PoE schedule/override/qualification, or within the 10-min boot grace after power returns) must:
  - **never** produce `device_offline` / `device_rebooted` incident signals, and never open or join an
    incident (also not via `mass_disconnect` of its clients);
  - show the device issue as `kind:'offline'`, `severity:'info'`, `messageKey:'infra.issue.poe_scheduled_off'`
    (params `{schedule}` = schedule/override name) instead of the error-level offline issue;
  - not count in `DashboardSummary.infra.offline`/`withIssues` (count it as online-planned);
  - still emit the `infra.offline` engine event, but with `planned: true` in the payload, and the
    `infra.offline` rule trigger must skip planned events unless a new optional trigger field is set — **do not
    change the contract**; simply skip planned events and document it.
- **Mock uptime must survive a Unifire restart.** Derive each mock device's uptime from a fixed boot timestamp
  persisted in the mock state (or a deterministic epoch), so restarting the server doesn't make every device
  look like it rebooted ("24 小時內曾非預期重開機" on all cards). Only the `reboot-ap` scenario and PoE power
  cycles may reset uptime.
